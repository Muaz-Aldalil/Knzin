# Glopale — Spec Kit Skill

**Glopale** provides the full [Spec Kit](https://github.com/github/spec-kit) spec-driven
development workflow inside Antigravity. It wraps the `specify` CLI (v1.0.11) and its
companion OpenCode commands as a single, unified skill.

> **Prerequisites**
> - `specify` CLI installed: `C:\Users\muaza\.local\bin\specify.exe`
> - Per-project `.specify/` scaffold — if missing, run Phase 0 (Init) below.

---

## Workflow Overview

```
/speckit.init  →  /speckit.constitution  →  /speckit.specify  →  /speckit.clarify
     →  /speckit.plan  →  /speckit.tasks  →  /speckit.implement  →  /speckit.converge
```

Each phase generates or updates files inside the project's `.specify/` directory.

---

## Phase 0 — Init (bootstrap per-project scaffold)

Run once per project when `.specify/` does not exist.

```powershell
specify init --here --force --non-interactive --integration opencode --ignore-agent-tools
```

This creates the `.specify/` directory with templates, constitution stub, and extension
config (`extensions.yml`).

**After init**, proceed to `/speckit.constitution`.

---

## Phase 1 — Constitution (`/speckit.constitution`)

Establish the non-negotiable principles for this project.

**What to do:**
1. Read `.specify/constitution.md` (generated by init).
2. Fill in the project-specific MUST/SHOULD principles (architecture, security, UX, etc.).
3. Save. This file is referenced by every downstream phase.

**Done when:** Constitution has at least one filled-in principle section.

---

## Phase 2 — Specify (`/speckit.specify <feature-description>`)

Write a business-level feature specification.

**What to do:**
1. Run `specify` or invoke this phase with a feature description as `$ARGUMENTS`.
2. Generate `.specify/<feature>/spec.md` following the spec template:
   - **Mandatory sections**: Summary, User Stories (with Acceptance Scenarios), Functional Requirements (FR-###), Success Criteria (SC-###)
   - **Optional sections**: Edge Cases, Assumptions, Out of Scope
3. Validation checklist — every item must pass:
   - [ ] Each requirement is testable and unambiguous
   - [ ] User stories follow "As a [role], I want [goal], so that [benefit]"
   - [ ] Success Criteria are measurable, technology-agnostic, user-focused, verifiable
   - [ ] No HOW (tech stack, frameworks, APIs) in the spec — only WHAT and WHY
   - [ ] Maximum 3 `[NEEDS CLARIFICATION]` markers for genuinely ambiguous decisions
4. If `[NEEDS CLARIFICATION]` markers remain, surface them (max 3) using this format:

   ```markdown
   ## Question [N]: [Topic]
   **Context**: [Quote relevant spec section]
   **What we need to know**: [Specific question]
   **Suggested Answers**:
   | Option | Answer | Implications |
   |--------|--------|--------------|
   | A      | ...    | ...          |
   | B      | ...    | ...          |
   **Your choice**: _[Wait for user]_
   ```

5. Check `.specify/extensions.yml` for `hooks.after_specify` hooks and dispatch them.

**Done when:** `spec.md` passes all checklist items and has no open clarifications.

---

## Phase 3 — Clarify (`/speckit.clarify`)

Interactive Q&A to resolve any remaining spec ambiguities before planning.

**What to do:**
1. Read `spec.md` and extract all unresolved questions / `[NEEDS CLARIFICATION]` markers.
2. For each (max 3), present options table (same format as Phase 2 step 4).
3. Wait for user answers, then update `spec.md` replacing markers with resolved answers.
4. Re-run spec validation after all clarifications.

---

## Phase 4 — Plan (`/speckit.plan`)

Create a technical implementation plan.

**What to do:**
1. Read `spec.md` (requirements, user stories).
2. Generate `.specify/<feature>/plan.md` containing:
   - Architecture / tech stack decisions
   - Data model (entities, relationships, constraints)
   - Interface contracts (API endpoints, function signatures)
   - Named touch-points: files and components that will be created or edited
   - Phases of delivery
   - Technical constraints and risks
3. Check `hooks.after_plan` in `.specify/extensions.yml` and dispatch.

**Done when:** `plan.md` covers all FR-### and maps them to concrete technical decisions.

---

## Phase 5 — Tasks (`/speckit.tasks`)

Break the plan into an executable, phase-organized task list.

### Task checklist format (REQUIRED for every task)

```
- [ ] T001 [P] [US1] <imperative description with exact file path>
```

| Component | Rule |
|-----------|------|
| `- [ ]`   | Always start with checkbox |
| `T###`    | Zero-padded sequential ID in execution order |
| `[P]`     | Include only if task is parallelizable |
| `[US#]`   | Required for User Story phase tasks; omit in Setup/Foundational/Polish phases |
| Description | Imperative verb + exact file path |

### Phase structure

- **Phase 1**: Setup (project initialization)
- **Phase 2**: Foundational (blocking prerequisites for all stories)
- **Phase 3+**: One phase per user story (in priority order P1, P2, P3…)
  - Each story phase: Models → Services → Endpoints/UI → Integration (→ Tests if TDD)
- **Final Phase**: Polish & cross-cutting concerns

### What to generate

1. Load `plan.md` (stack, architecture, touch-points) and `spec.md` (user stories, priorities).
2. Map every FR-### and acceptance scenario to tasks in the appropriate phase.
3. Include dependency graph (story completion order) and parallel execution examples.
4. Validate: each story has all needed tasks, independently testable.

**Done when:** `tasks.md` has all phases, IDs, file paths, dependency graph.

---

## Phase 6 — Checklist (`/speckit.checklist`)

Generate a quality checklist for the feature.

**What to do:**
1. Read `spec.md` and `plan.md`.
2. Produce `.specify/<feature>/checklist.md` — one checkbox per acceptance scenario,
   success criterion, and critical edge case.
3. Checklist items must be independently verifiable without knowing implementation details.

---

## Phase 7 — Implement (`/speckit.implement`)

Execute the task list and build the feature.

### Pre-flight

1. Load progressive context (minimal required for current task):
   - `spec.md` → Functional Requirements + Success Criteria + User Stories
   - `plan.md` → Stack decisions + named touch-points + technical constraints
   - `tasks.md` → Task IDs, phases, descriptions, file paths

2. Check `hooks.before_implement` in `.specify/extensions.yml`.

### Execution loop

For each unchecked task in `tasks.md` (ordered by phase, then ID):
1. Complete the task (write/edit code at the specified file path).
2. Mark the checkbox: change `- [ ]` to `- [x]`.
3. Move to the next task.

Parallelizable tasks (`[P]`) may be executed concurrently when there are no dependency conflicts.

### Extension hooks (after_implement)

After all tasks are done, check `hooks.after_implement` and dispatch. Mandatory hooks (`optional: false`) MUST be executed:

```
## Extension Hooks
**Automatic Hook**: {extension}
Executing: `/{command}`
EXECUTE_COMMAND: {command}
```

**Done when:** All tasks checked, hooks dispatched, completion reported.

---

## Phase 8 — Converge (`/speckit.converge`)

Verify the implementation satisfies the spec and append remediation tasks for any gaps.

### Steps

1. Load `spec.md`, `plan.md`, `tasks.md`, and constitution.
2. Build **Intent Inventory**: one stable key per FR-###, SC-###, user-story acceptance scenario, plan decision, constitution principle.
3. Derive **code-scope map** from file paths named in `plan.md` and `tasks.md`.
4. Assess each inventory item against the current code. Produce a `Finding` only where a gap exists.

### Gap types

| Gap Type | Meaning |
|----------|---------|
| `missing` | Required work is entirely absent |
| `partial` | Exists but doesn't fully satisfy the requirement |
| `contradicts` | Code conflicts with stated intent or a constitution MUST principle |
| `unrequested` | Code contains work not called for by spec/plan/tasks |

### Severity

| Severity | Criteria |
|----------|----------|
| CRITICAL | Violates constitution MUST, or missing/contradicts blocking a P1 story |
| HIGH | Missing or partial on a core FR or acceptance criterion |
| MEDIUM | Partial on secondary requirement, or unrequested with unclear justification |
| LOW | Minor partial, polish, or low-risk unrequested additions |

### Output

**Present findings summary first (before any file writes):**

```markdown
## Convergence Findings
| ID | Gap Type | Severity | Source | Evidence | Remaining Work |
|----|----------|----------|--------|----------|----------------|
| F1 | missing  | HIGH     | FR-008 | <evidence> | <work> |
```

**If findings exist** — append to `tasks.md`:
- Find max existing task ID `M` and highest phase `N`.
- Append `## Phase {N+1}: Convergence` with one task per finding, CRITICAL/HIGH first:
  ```
  - [ ] T{M+1:03d} <imperative description> per <source-ref> (<gap-type>)
  ```
- Never reuse or renumber existing IDs.

**If no findings** — do NOT modify `tasks.md`. Report:
> ✅ **Converged** — the implementation satisfies the spec, plan, and tasks.

Then dispatch `hooks.after_converge`.

## Analyze (`/speckit.analyze`)

On-demand: assess the codebase against the spec without appending tasks. Produces the
same Convergence Findings table but takes no action. Use to get a status snapshot at any
point in the implementation.

---

## Tasks to Issues (`/speckit.taskstoissues`)

Convert `tasks.md` checklist items into GitHub Issues.

**What to do:**
1. Parse `tasks.md` — extract Task ID, labels (`[P]`, `[US#]`), description, file path.
2. For each unchecked task, create a GitHub Issue with:
   - Title: Task ID + description
   - Labels: story label, `spec-kit`, phase
   - Body: link to source task in `tasks.md`, file path, parent user story
3. After creation, optionally update `tasks.md` to hyperlink each task ID to its Issue.

---

## Code Review (`/skill:code-review` or activate via this skill)

Reviews Spec Kit code changes for quality.

1. Ensure each code change has test cases for both positive and negative paths.
2. Bug-fix PRs must include a regression test demonstrating the bug was reproducible before and fixed after the change.
3. Wording changes must use repository-consistent terminology (excluding community-authored catalog content).

---

## Add Community Extension

Process a community extension submission issue and add it to the catalog.

### Procedure

1. Fetch the GitHub issue and extract: ID, name, version, description, author, repo URL, download URL, license, required spec-kit version, commands count, hooks count, tags.
2. Validate all publishing rules:
   - Repository exists and is public
   - `extension.yml`, `README.md`, `LICENSE` present
   - GitHub release matching the version exists
   - Download URL follows `archive/refs/tags/vX.Y.Z.zip` pattern
   - Extension ID: `^[a-z][a-z0-9-]*$`
   - Version: semver `X.Y.Z`
   - All submission checklists checked in the issue body
3. Update `extensions/catalog.community.json` (alphabetical order by ID; preserve `created_at`/`downloads`/`stars` on updates).
4. Update `docs/community/extensions.md` table (alphabetical by name).
5. Validate JSON: `python3 -c "import json; json.load(open('extensions/catalog.community.json')); print('Valid JSON')"`
6. Commit with message `Add <Name> extension to community catalog` (or `Update <Name> extension to v<version>`), push, open PR with `Closes #<issue-number>`.

## Common Pitfalls

- **`.specify/` missing** — run `/speckit.init` first before any other phase command.
- **Tasks without file paths** — every task in `tasks.md` MUST include an exact file path.
- **Spec contains HOW** — specs should describe WHAT and WHY only; move technical details to `plan.md`.
- **Reusing task IDs in converge** — always scan for the highest existing ID and start from `M+1`.
- **JSON not validated after catalog edit** — always run the `python3` validation snippet after editing `catalog.community.json`.
- **`created_at` reset on extension update** — preserve the original `created_at`; only update `updated_at`.
