## GC-4 Payout receipt storage (filesystem is not part of the DB transaction)
Pipeline: **upload → validate → stage on private disk → hash → settlement DB transaction → authoritative receipt reference**.
1. Validate (`image`, jpg/jpeg/png/webp, content-sniffed MIME, ≤ 5 MB — engineering security limits, configurable); cheap pre-read of payout state (fast 409/replay without writing a file).
2. Write to private `payout-receipts` disk under a random ULID key; read back size + `sha256`; verify.
3. Call `AffiliatePayoutService::settlePayout(...)` (GC-16/GC-5). Inside its transaction, the **last** statement sets `committedClosure = true`; any exception thrown after that point is wrapped in `AmbiguousCommitException`.
4. Controller cleanup: any exception **except** `AmbiguousCommitException` ⇒ delete the staged file (definitive rollback, incl. 409/422/audit failure). `AmbiguousCommitException` ⇒ **keep** the file and reconcile by re-reading the payout (`completed` + this `receipt_path` ⇒ success). An idempotent replay (GC-16) deletes its newly staged file. No filesystem operation occurs after commit.
- **Never produced: completed payout + missing required receipt.** `settlePayout` requires non-empty `receiptPath` + `receiptSha256` (else exception before any write); the file was verified on private disk before the transaction began. (Streaming download endpoint is omitted per US4; receipt metadata and sha256 are stored authoritatively on the payout record).
- Crash/retry: crash between steps 2 and 3 ⇒ unreferenced private orphan (harmless; a report-only reconciliation command is listed under *Possible*); retry stages a new key; double-submit ⇒ second request is an idempotent replay or a 409, never a second receipt. Pre-F008 completed payouts have no receipt (legacy; the guarantee applies to payouts settled through F008).

## GC-5 Audit transaction ownership (no controller wrapper, no executor)
Flow: **Admin Controller → authorization (Gate in service) → authoritative service → service-owned `DB::transaction` → domain mutation → `admin_activity_logs` write (last statement) → commit.** Any audit failure throws ⇒ the service's transaction rolls back the domain mutation.
- `AdminAuditContext` (readonly value object: actor id, capability used, request id, ip hash, optional justification) is built by the controller/FormRequest and passed into the service. `AdminAuditWriter::record($ctx, $action, $targetType, $targetId, $before, $after)` is called by the service as its last in-transaction statement. `before_state` is read after the row lock. `AdminActionExecutor` is **removed** from the plan (verified need: none — every operation is a single service call; the nested-savepoint trick is unnecessary).
- Existing services get **backward-compatible optional trailing `?AdminAuditContext`** (CLI/tests pass none): `PlatformSettingsService::setMany()` (new method; `set()` unchanged), `AffiliatePayoutService::settlePayout/rejectPayout` (signature refactored anyway), `AffiliateCoPrizeService::adjudicateCoPrizeRelease` (new) / `adjudicateCoPrizeRevocation`, `ApprovalRegistryService` issue/revoke. New services own their transaction and require the context: `AdminCapabilityService`, `DrawLifecycleService` (incl. `DrawSeedService` helper), `PrizeService`, `PromotionalAwardService`.
- Enforcement that no admin mutation skips audit: `AdminAuditCoverageTest` invokes **every mutating admin route** on its happy path and asserts exactly one `success` audit row; `AdminAuditAtomicityTest` binds a throwing `AdminAuditWriter` per operation and asserts zero domain change. CLI commands remain out-of-band (documented residual, Feature 006 behavior).
- Failure/denial rows (`denied|rejected|conflict|failed|replay`) are written by the terminating `AuditAdminFailures` middleware **outside** any transaction; write failure ⇒ `Log::critical`, never alters the response.
- Single attempt per transaction (no retry loop): a deadlock surfaces as 500 + failure row; simpler and idempotent by design.

## GC-16 Payout state-transition remediation (implementation sequence and tests; see also GC-4)
Evidence: [AffiliatePayoutService L121-L162](https://github.com/Muaz-Aldalil/Knzin/blob/c0042c52741a4943fef3442af9b9ad7a5b098d56/backend/app/Services/AffiliatePayoutService.php) ignores the `bool` from `markCompleted()/markRejected()` ([AffiliatePayout](https://github.com/Muaz-Aldalil/Knzin/blob/c0042c52741a4943fef3442af9b9ad7a5b098d56/backend/app/Models/AffiliatePayout.php) returns `false` unless status ∈ `requested|processing`). Request path creates the debit as `payout_debit`, status **`available`**, key `payout_debit_{number}`; settle later sets it `cleared`; reject appends `reversal_credit` key `payout_reversal_{number}`. **Confirmed defects**: settle on a rejected payout clears a reversed debit; reject on a completed payout appends an unintended credit.

**Mandatory sequence (inside the service transaction):**
`Gate` (before tx) → re-fetch payout by id with `lockForUpdate` → anti-self guard → verify state:
- settle: `requested|processing` proceed; `completed` with the **same** `admin_reference_number` ⇒ **idempotent replay** (HTTP 200, `idempotent_replay:true`, zero writes, replay row); `completed` with a different reference or `rejected` ⇒ `PayoutStateConflictException` (409).
- reject: `requested|processing` proceed; `rejected` ⇒ idempotent replay; `completed` ⇒ 409.
→ execute `markCompleted()/markRejected()` and **verify the returned `true`** (else throw) → ledger step: settle updates **exactly** the entry `idempotency_key = payout_debit_{number}` (`payout_id` = this payout, status `available`→`cleared`) and verifies **affected rows === 1**; reject inserts the `reversal_credit` and verifies exactly one exists for this payout → `AdminAuditWriter::record` → commit. Any failed check ⇒ exception ⇒ rollback ⇒ **zero financial side effects**.
Required tests (`AdminPayoutStateTransitionTest`, `AdminPayoutConcurrencyTest`): rejected→settle blocked; completed→reject blocked; completed→settle idempotent (same ref) and conflict (different ref); rejected→reject idempotent (one reversal row, balance restored once); concurrent settle vs reject via interleaving (second connection holding the row lock ⇒ exactly one terminal state, ledger consistent); missing-debit ⇒ rollback; throwing audit ⇒ rollback; receipt orphan cleanup (GC-4). Update the three call sites (`AffiliatePayoutLifecycleTest` L138/L193, `AffiliateAcceptanceScenariosTest` L337).
Payout threshold is the minimum **available balance at request time** (`threshold_cents_at_request` snapshot); settle/reject never recompute it. **Removed** the invented unique constraint on `admin_reference_number` (a reused MTCN is not a PO rule): plain index only; a duplicate reference is surfaced as an audit warning, not blocked.

**Conclusion: not a breaking API change.** Rule: `completed ⇒ completed`; `now >= ends_at ⇒ locked`; stored `upcoming` ∧ `is_published` ∧ `starts_at <= now < ends_at` ⇒ `active`; else stored. **Nothing is persisted**; stored history is untouched. The admin read model's `lifecycle_stage` (`draft|upcoming|active|locked|completed`) calls the same method (single calculation). Manual admin `active`/`locked` transitions are **removed** (no consumer; would contradict window-derived eligibility).

### 7.2 Schedule editing (`starts_at`, `ends_at`) — the unsupported freeze is REMOVED
Both fields stay **Admin-editable in every state including active and locked draws**, because the PO approved broad live editing. The only constraints are genuine integrity ones:
1. `ends_at > starts_at`.
2. **Commitment before accumulation (Constitution IX step 1; spec US6 AC2, FR-013, SC-008)**. The requirement is only "the hash is public **before** accumulation opens". It is implemented as (a) the publish guard `now < starts_at` (so the first commitment precedes the window) and (b) the *same invariant preserved under later edits*: a draw that already has a committed seed may not have `starts_at` set earlier than `seed_committed_at` (otherwise the window would open before the commitment existed). No other relationship is imposed (no minimum gap, no "starts_at must be after publish by N", legacy draws with no seed are unconstrained). The spec does not state `starts_at >= seed_committed_at` literally; it is the logical post-condition of the constitutional rule and is classed INTEGRITY, not a business rule.
3. **Canonical result protection (narrow, INTEGRITY)**: if a `draw_winners` row exists for the draw, `starts_at`/`ends_at` are read-only. Authority: spec FR-014 ("strictly prohibiting modification of ... ticket allocations, and canonical winner records") and Constitution IX steps 3–4 (winner = `HMAC(server_seed, client_seed) % total_tickets` over the ticket set the window defines; the public must be able to re-verify). Repository evidence: tickets are not draw-bound, so the window *is* the ticket allocation (`TicketController` eligibility `starts_at <= issued_at < ends_at`). This is **not** a generic "read-only after winner": every other operational field stays editable (see 7.3). It is a single guard keyed on the existence of the `draw_winners` row (not on `completed`, not on `now`), checked under `lockForUpdate` on the draw row; any future winner-creating component MUST lock the same row.
No other freeze (the earlier "`ends_at` frozen once `now >= ends_at`" rule is deleted). Because tickets are not draw-bound and eligibility is computed at read time, a schedule change rewrites no stored ticket fact; the audit row records the count of tickets whose eligibility changes (transparency, not a restriction); an optional justification is accepted.

### 7.4 Completion never manufactures a result
`POST /draws/{id}/complete` **records completion of an already-established canonical result**. Preconditions: draw published and a `draw_winners` row with this `draw_id` **already exists**; otherwise `409 ERR_CANONICAL_RESULT_MISSING` with no status change, no seed reveal, no winner write (failure audit row only). The Admin Panel never selects a winner, never creates/updates/deletes `draw_winners` rows (only the four display-metadata columns via `PATCH …/winner`), and exposes the result/evidence read-only in `GET /draws/{id}`. Completion on an already-`completed` draw is an idempotent replay. A draw without a commitment (legacy) completes without a reveal. Tests: no-winner ⇒ 409 and zero writes; `draw_winners` row count/columns unchanged across every admin operation; static test that nothing under `app/Services/Admin`, `app/Http/Controllers/Admin` or the draw services calls a write on `DrawWinner` other than the metadata update. DP-2 (repository evidence): Production canonical-winner ownership is not proven by repository evidence; no production runtime component creates winners today ⇒ `complete`, reveal and the co-prize queue are verified with fixtures and inert in production until a draw engine exists.

### 7.5 Publish is atomic; the seed never leaks
`DrawLifecycleService::publish` runs in **one service-owned `DB::transaction`**: `lockForUpdate` draw → guards (`is_published=0`, seed absent, `now < starts_at`) → `random_bytes(32)` → lowercase hex (in memory only) → `server_seed_hash = sha256(hex)` → `Crypt::encryptString(hex)` → **single UPDATE** setting `server_seed_hash`, `server_seed_encrypted`, `seed_committed_at`, `is_published=1`, `published_at/by` → self-check (decrypt + re-hash equals stored hash; failure ⇒ throw) → audit (hash only) → commit. Table CHECKs (`chk_draws_seed_atomic`, draft⇒upcoming) back this at schema level. Any failure ⇒ rollback ⇒ no seed, no hash, still a private draft; a retry generates a fresh seed. No external side effect exists. Plaintext seed: never logged, never in API/audit/exception context (methods receiving it use `#[\SensitiveParameter]`, PHP ≥ 8.2 per `composer.json`), never serialized (`$hidden`, not fillable); exposed only by the authorized reveal. Reveal happens only inside `complete` (7.4): `hash_equals(sha256(decrypted), server_seed_hash)`, then one-way write of `server_seed_revealed`. APP_KEY loss makes the seed unrecoverable (risk R-7; reveal fails closed). Tickets first count at `starts_at`; the commitment is authoritative at the publish commit, which precedes it.
